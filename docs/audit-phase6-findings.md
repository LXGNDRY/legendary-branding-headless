# Audit Phase 6 — Accessibility & Performance: Findings

Ref: `docs/full-site-audit-plan.md` Phase 6. Status legend: **Pass** / **Gap** / **Fixed**.

| # | Item | Status | Detail |
|---|---|---|---|
| 26 | Automated a11y audit (axe/Lighthouse) across golden-journey routes | **Fixed** | No automated accessibility testing existed anywhere in the repo prior to this — confirmed via dependency grep (`axe`/`lighthouse` absent from `package.json`) and a search of `e2e/` (a false-positive substring match on "taxes" was the only hit). Added `@axe-core/playwright` as a devDependency and a new `e2e/a11y.spec.ts` auditing the 6 golden-journey routes most representative of real traffic (homepage, collections index, all-products collection, journal index, cart, search) against WCAG 2.0/2.1 A+AA rule tags. The test fails on any violation axe returns from that WCAG-tag-restricted audit, regardless of impact severity — severity measures how badly a violation affects users, not whether the underlying rule is in scope, and the tag filter already restricts results to normative WCAG AA rules, so filtering by impact on top of that would let real, in-scope violations pass silently (Codex caught this on the first review pass; fixed before merge). Runs automatically in CI as part of the existing E2E matrix (same `*.spec.ts` glob, same browser projects) — this phase could not execute it end-to-end in this sandbox (no live Storefront credentials, the same documented limitation hit in earlier phases), so its first real run will be in CI on this PR. |
| 27 | Raw `<img>` sweep (should be zero) | Pass | Re-confirmed, repo-wide: zero raw `<img>` tags remain except the one deliberate, already-reviewed exception in `HeroSplit.tsx` (Phase 5's findings — responsive art-direction `<picture>` that Hydrogen's `<Image>` can't express). Every fix from Phase 5 holds. |
| 27 | CDN domain + explicit width/height on images (CLS prevention) | Pass | Sampled across the fixes made in Phases 4-5 (`account.orders.tsx`, `Lookbook.tsx`, `RecentlyViewed.tsx`, `SearchTypeahead.tsx`, `ContentBlocks.tsx`) plus pre-existing `<Image>` usages (`ProductCard`, `ProductGallery`, hero/section components) — all resolve through Shopify's `cdn.shopify.com` and all pass explicit `width`/`height`. |
| 26 | Real finding surfaced by the new a11y suite's first live run | **Fixed** | CI caught a genuine, sitewide WCAG AA color-contrast failure on its very first run: `text-white` on `bg-[var(--color-accent)]` (#E63936 brand red) measures 4.19:1, below the 4.5:1 required for normal-size text — axe flagged it as `serious` on every one of the 6 audited routes via the newsletter footer form, but the same `bg-accent` + `text-white` pattern was used for the primary site-wide CTA button (`Button.tsx`'s `primary` variant — "Shop Now", "Add to Cart", etc.), the sale `Badge`, the cart-count badge and promo pills in `Header.tsx`, the `ChatWidget`, the skip-to-content link in `root.tsx`, and a PDP "Save $X" badge. The design system already had the correct token for this (`--color-text-inverse: #0A0A0A`, documented as "text on accent / light surfaces") and two components (`BeforeAfter.tsx`, `FitCheck.tsx`) already used it correctly — the rest had drifted to `text-white` instead. Switched all 9 affected call sites to `text-[var(--color-text-inverse)]` (black-on-accent-red measures ~4.72:1, passing AA). One additional latent instance was found in `EditorialBand.tsx`'s unused `theme="accent"` branch (never invoked anywhere in the app today — only `theme="dark"` is used) — left as a documented, out-of-blast-radius gap rather than fixed, since fixing its opacity-based white variants (`text-white/70`, `text-white/80`) correctly requires recalculating contrast at each opacity level, which isn't exercised by anything live today. |
| 28 | Bundle-size baseline / regression check | **Fixed (baseline recorded)** | No recorded baseline existed to check against. Recorded one from this phase's `npm run build` output (client bundle, gzip-uncompressed byte sizes from Vite's manifest): largest chunks are `index-*.js` (~494 KB, the shared vendor/React chunk), `entry.client-*.js` (~141 KB), and a secondary vendor chunk (~132 KB); every route-level chunk is well under 40 KB, with most resource routes (`api.*`, `[robots.txt]`, `[sitemap.xml]`, `[site.webmanifest]`) correctly tree-shaken to a 1-byte stub (no client JS needed for a pure-loader resource route). No new large client-side dependency was added this audit — the only new dependency (`@axe-core/playwright`) is a devDependency used solely in `e2e/`, never bundled into the shipped app. Future phases/PRs should diff `npm run build`'s Vite output against these figures and flag any route-level chunk that newly exceeds ~50 KB or any new top-level vendor chunk. |

## Summary
2 real, fixed gaps: zero automated accessibility testing existed despite CLAUDE.md's explicit WCAG AA requirement (added a real axe-core-based E2E suite covering the 6 highest-traffic routes), and that very suite's first live run immediately caught a genuine sitewide WCAG AA color-contrast failure affecting the primary CTA button and 8 other components, now fixed by switching to the design system's own already-correct (but under-used) inverse-text token. The raw-`<img>`/CLS sweep re-confirmed Phase 5's fixes hold with no regressions. Bundle size has no prior regression to compare against but now has a recorded baseline for future phases to check against, and no unjustified new client-side dependency was found. Full local gate (`build && typecheck && lint && test`) green throughout.

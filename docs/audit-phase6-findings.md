| 26 | Automated a11y audit (axe/Lighthouse) across golden-journey routes | **Fixed** | No automated accessibility testing existed anywhere in the repo prior to this — confirmed via dependency grep (`axe`/`lighthouse` absent from `package.json`) and a search of `e2e/` (a false-positive substring match on "taxes" was the only hit). | 26 | Real finding surfaced by the new a11y suite's first live run | **Fixed** | CI caught a genuine, sitewide WCAG AA color-contrast failure on its very first run: `text-white` on `bg-[var(--color-accent)]` (#E63936 brand red) measures 4.19:1, below the 4.5:1 required for normal-size text — axe flagged it as `serious` on every one of the 6 audited routes via the newsletter footer form, but the same `bg-accent` + `text-white` pattern was used for the primary site-wide CTA button (`Button.tsx`'s `primary` variant — "Shop Now", "Add to Cart", etc.), the sale `Badge`, the cart-count badge and promo pills in `Header.tsx`, the `ChatWidget`, the skip-to-content link in `root.tsx`, and a PDP "Save $X" badge. The design system already had the correct token for this (`--color-text-inverse: #0A0A0A`, documented as "text on accent / light surfaces") and two components (`BeforeAfter.tsx`, `FitCheck.tsx`) already used it correctly — the rest had drifted to `text-white` instead. Switched all 9 affected call sites to `text-[var(--color-text-inverse)]` (black-on-accent-red measures ~4.72:1, passing AA). One additional latent instance was found in `EditorialBand.tsx`'s unused `theme="accent"` branch (never invoked anywhere in the app today — only `theme="dark"` is used) — left as a documented, out-of-blast-radius gap rather than fixed, since fixing its opacity-based white variants (`text-white/70`, `text-white/80`) correctly requires recalculating contrast at each opacity level, which isn't exercised by anything live today. |
| 26 | Second real finding: focusable content inside `aria-hidden` containers | **Fixed** | After fixing the contrast issue, the stricter "fail on every WCAG-tagged violation" assertion surfaced a second real, pre-existing bug: the mobile menu (`Header.tsx`) and cart drawer (`CartDrawer.tsx`) both set `aria-hidden={!open}` on their dialog container when closed, but only move it off-screen via a CSS transform -- their links/buttons remain in the DOM and keyboard-focusable the whole time, so a sighted keyboard user tabbing through the closed page lands on invisible, hidden-from-screen-readers controls (axe's `focusable-disabled`/`focusable-not-tabbable` rules, both WCAG 2 A). Fixed by adding the `inert` DOM attribute alongside `aria-hidden` on both containers when closed -- `inert` removes an element from the tab order and from assistive-tech focus, which `aria-hidden` alone does not do. The first attempt passed `inert` as a spread JSX prop cast to `{inert?: boolean}`, since `@types/react` 18.3 doesn't declare it; CI's next run showed the violation persisting, because React stringifies an unrecognized attribute's boolean `false` as the literal text `inert="false"` rather than omitting it, and *any* string value (even `"false"`) makes an element inert to the browser -- not what was intended. A second attempt set/removed the attribute imperatively via a `useEffect` + ref, which also failed intermittently in CI -- `useEffect` only runs client-side after hydration, so it couldn't fix the server-rendered HTML axe saw first, creating a timing race (flaky rather than consistent). The correct fix: pass `inert` a real string value (`''` when present, `undefined` when not) instead of a boolean -- rendered synchronously during SSR, so it's correct in the initial HTML, and a string has none of the boolean-stringification ambiguity. Also fixed a third, related element this same CI run flagged: `AnnouncementBar.tsx`'s scrolling marquee wraps its (intentionally aria-hidden, decorative/duplicative) announcement links without `tabIndex={-1}`, so they stayed keyboard-focusable despite the row being hidden from screen readers -- added `tabIndex={-1}` to its `<Link>` rather than `inert`, since a sighted mouse user should still be able to click it. A fourth, unrelated finding (mobile viewport only): `collections.$handle.tsx`'s sort `<select>` has a sibling `<span>Sort</span>` label, but it's `hidden sm:block` -- hidden below the `sm` breakpoint -- and not programmatically associated with the select either way (no `htmlFor`/`id`, no `aria-label`), so on mobile the select has literally no accessible name at all (axe's `select-name`, WCAG 2 A). Fixed with `aria-label="Sort products"`. |
| 26 | Third real finding: journal article links with no accessible name | **Fixed** | A third real bug surfaced once the stricter assertion ran clean of the first two: `journal._index.tsx`'s article-card and featured-article `<Link>` wrap only an `<Image>` (or, when `article.image` is falsy, an empty placeholder `<div>`) with no separate visible text and no `aria-label` -- when an article has no image, its card link has literally no accessible name at all (axe's `link-name`, WCAG 2 A/AA). The sibling `collections._index.tsx` card pattern doesn't have this bug because it always renders visible title text as a sibling of the image inside the link; journal's cards don't. Fixed by adding `aria-label={article.title}` / `aria-label={featured.title}` to both links. |
| 26 | Fifth real finding: `dt`/`dd` not direct children of `dl` | **Fixed** | A fifth real bug surfaced once the first four were clean (mobile viewport, homepage route): `StatStrip.tsx` rendered each `<dt>`/`<dd>` pair wrapped inside an intermediate `<div role="listitem">`, so the `dt`/`dd` elements were grandchildren of the `<dl>`, not direct children -- axe's `dlitem` rule (WCAG 1.3.1, `serious`) requires the direct-child relationship regardless of any ARIA role override on an ancestor, because screen readers also key off the native `dt`/`dd` semantics themselves, not just the containing list's role. The component was already overriding semantics with explicit `role="list"`/`role="listitem"` on the `<dl>`/wrapper `<div>` -- a signal it was never really modeling a term/definition pair, just reusing those tags for their default stacked-block layout -- so the correct fix was to drop the `dl`/`dt`/`dd` tags entirely in favor of plain `div`s, keeping the existing `role="list"`/`role="listitem"` attributes (and all layout classes) unchanged. No visual or semantic regression: the ARIA roles already fully expressed the intended list structure independent of the underlying tag names. |
| 28 | Bundle-size baseline / regression check | **Fixed (baseline recorded)** | No recorded baseline existed to check against. Recorded one from this phase's `npm run build` output (client bundle, gzip-uncompressed byte sizes from Vite's manifest): largest chunks are `index-*.js` (~494 KB, the shared vendor/React chunk), `entry.client-*.js` (~141 KB), and a secondary vendor chunk (~132 KB); every route-level chunk is well under 40 KB, with most resource routes (`api.*`, `[robots.txt]`, `[sitemap.xml]`, `[site.webmanifest]`) correctly tree-shaken to a 1-byte stub (no client JS needed for a pure-loader resource route). No new large client-side dependency was added this audit — the only new dependency (`@axe-core/playwright`) is a devDependency used solely in `e2e/`, never bundled into the shipped app. Future phases/PRs should diff `npm run build`'s Vite output against these figures and flag any route-level chunk that newly exceeds ~50 KB or any new top-level vendor chunk. |

## Summary
5 real, fixed gaps: zero automated accessibility testing existed despite CLAUDE.md's explicit WCAG AA requirement (added a real axe-core-based E2E suite covering the 6 highest-traffic routes), and that very suite's first four live CI runs each caught a genuine, pre-existing WCAG AA bug -- a sitewide color-contrast failure on the primary CTA button and 8 other components (fixed via the design system's own already-correct but under-used inverse-text token), a focusable-content-while-hidden bug in the mobile menu and cart drawer (fixed with the `inert` attribute, plus a related marquee-link fix and a mobile-only sort-`<select>` accessible-name fix found in the same run), journal article-card links with no accessible name when the article has no image (fixed with `aria-label`), and a `StatStrip.tsx` structural bug wrapping `dt`/`dd` in an intermediate `<div>` instead of making them direct children of `<dl>` (fixed by dropping the definition-list tags in favor of plain `div`s, since the component already expressed its real semantics via explicit ARIA roles). The raw-`<img>`/CLS sweep re-confirmed Phase 5's fixes hold with no regressions. Bundle size has no prior regression to compare against but now has a recorded baseline for future phases to check against, and no unjustified new client-side dependency was found. Full local gate (`build && typecheck && lint && test`) green throughout.
